# ArchGuard 扫描、架构检测与项目计划落地方案

## 交付边界

公开 Git 仓库扫描、架构检测和计划基线已接入工作台。后续可通过稳定的模块路径和任务编号接入变更分析。总体设计见 [Web 架构设计](web-architecture.md)。

## 本阶段 · Git 仓库扫描

- [x] 从项目页面提交默认分支、分支名、完整引用或提交 SHA，将任务持久化并交给扫描进程。
- [x] 用临时裸仓库浅取指定版本，记录提交 SHA。用 Git 对象读取 JS/TS 源码及解析配置，提取文件、内部依赖及其行号，单列外部和未解析引用。
- [x] 保存历史摘要与结果详情。在页面中查看状态、提交、依赖表和扫描缺口，保留环境检查入口。
- [x] 用真实仓库验证提交与依赖，用本地样例验证路径别名、重新导出、类型依赖和覆盖率缺口。

采用裸仓库和虚拟文件系统解析。这样能按提交复现扫描，仓库内容也不会落入本机工作树。当前工作台仍按单机、单 Worker 运行。

## 工作包 A · 架构检测

| 步骤 | 实现位置 | 可验收结果 |
| --- | --- | --- |
| A1 配置扫描规则 | `apps/api/src/scans`、`packages/contracts` | 录入分层路径前缀和允许的有向依赖。匹配重叠需明确优先级，未归层文件单列 |
| A2 执行规则 | 新建 `apps/api/src/architecture`，由 Worker 调用 | 对内部边运行强连通分量检测。对跨层边检查允许表。每条问题有规则编号、路径、行号和稳定指纹 |
| A3 保存和展示 | SQLite 扫描结果、`apps/web/src/pages/RepositoryScansPage.tsx` | 历史扫描保留规则快照和版本。在依赖图或表中筛选问题，点击查看触发边与源码位置 |
| A4 复扫对比 | 架构模块与扫描详情页 | 在同一规则版本、扫描范围和解析器版本下比较新增、仍存在及不再检出的问题 |

循环规则以至少两个互相可达的文件为一个组，自导入也算一个组。每组提供一条真实闭合路径。分层规则按有向边逐条判断，并记录命中规则。首版单独展示类型依赖，默认只对运行期静态边判定循环。规则输入应保留分组、边类别、适用范围及覆盖情况。指纹以规则编号和稳定路径为基础，避免移动行号引起误判。

验收样例包括三文件成环、无环链、自导入、同一层内依赖、禁止的跨层导入、缺失分层映射。移除环中一条边后复扫，应能指出旧问题不再检出。扫描有缺口时显示限制，结论保留人工复核状态。

## 工作包 B · 项目计划基线

| 步骤 | 实现位置 | 可验收结果 |
| --- | --- | --- |
| B1 定义导入格式 | 新建 `apps/api/src/plans`，共享类型放入 `packages/contracts` | 支持一份按需求编号分段的 Markdown 和一份 UTF-8 任务 CSV，预览后确认导入 |
| B2 校验并保存 | SQLite `plan_versions` 表和计划模块 | 校验唯一编号、引用、重复边、任务环、非负工时与费率。成功时原子创建基线快照并更新当前版本 |
| B3 计算基线 | 计划模块内独立排程函数 | 任务拓扑排序后计算最早开始与完成、交付工期、总人时、人工成本及关键路径 |
| B4 展示和关联 | 新建 `apps/web/src/pages/PlansPage.tsx` | 查看任务列表和依赖，确认需求到任务、任务到代码路径的关联，查阅旧版本 |

需求文档示例用 `## REQ-07 导出审计记录` 开头。CSV 建议使用 `id,title,requirementIds,predecessorIds,effortHours,durationDays,hourlyRate,modulePaths`，多值字段用竖线分隔。任务和需求使用稳定编号，模块关联使用仓库相对路径或目录前缀，关联缺失时标记待确认。计划接口可用 `POST /api/projects/:projectId/plan-versions` 创建基线，`GET /api/projects/:projectId/plan-versions` 读取历史。

工期在同一工作日起点计算。任务最早开始为所有前置任务最早完成的最大值，完成时间加任务持续时长。持续时长缺省时按人时除以每日有效投入，课程样例取 8 人时。人工成本按任务工时乘费率后求和。任务可以并行，资源冲突和节假日留到后续。

验收样例包含两条分别为 4 日和 5 日的并行任务链，基线交付应为第 5 个工作日。将较短路径增加 1 日后，工作量和成本增加，交付仍为第 5 日。再增加 2 日则交付为第 7 日。任务环、重复编号与缺失前置应拒绝导入，旧基线仍可读取。

## 接通两个工作包

1. 变更分析读取指定 `scanId` 与 `planVersionId`，通过任务的代码路径映射汇合两张依赖图。实际改动、复核和排期影响分别记录。
2. 以基线和三种任务差异复用同一排程函数。保存工时、成本和交付变化的计算输入。
3. 选择一个真实 JS/TS 项目的固定提交，手工核对扫描边和受影响任务。用同一案例完成审批、代码修改、测试、复扫与报告。
